# コンテンツ更新取扱説明書

この文書は、「もっと住みやすい高槻へ」を、非エンジニアでも安全に更新・運用できるようにするための実務マニュアルです。

**「何をしたいか」から該当する項目を探してください。**

この文書では、

* 何を自分で変更してよいか
* どのファイルを変更するか
* 変更するときに何を一緒に確認するか
* 何を変更してはいけないか
* YouTube・X・Instagram・noteをどう扱うか
* 政策ページを新しく作る方法
* 活動ページを新しく作る方法
* 公開前・公開後に何を確認するか
* 分からないときにAIへどう依頼するか

をまとめています。

---

# 1. 最初に：このサイトの情報はどこにあるか

このサイトでは、情報の種類ごとに保存場所が分かれています。

| 情報        | 保存場所                      | 主な用途             |
| --------- | ------------------------- | ---------------- |
| 政策        | `src/content/policies/`   | 政策ページ            |
| 活動        | `src/content/activities/` | 活動記録             |
| 出典        | `src/content/sources/`    | 政策等で参照する資料       |
| 固定ページ     | `src/content/pages/`      | 利用規約・プライバシーポリシー等 |
| 共通設定      | `src/data/`               | SNS、政党情報、カテゴリー等  |
| 共通CSS     | `src/styles/global.css`   | サイト全体のデザイン       |
| ページ・表示    | `src/pages/`              | ページの仕組み          |
| 部品        | `src/components/`         | 共通UI部品           |
| データschema | `src/content.config.ts`   | Markdownのデータ構造   |

**原則として、日常的な情報更新は `src/content/` のMarkdownを編集します。**

# 2. まず覚える「自分で触ってよい場所」と「触らない場所」

## 2-1. 🟢 原則として自分で触ってよい

通常の情報更新では、次の場所を使用します。

### 政策

```text
src/content/policies/
```

### 活動

```text
src/content/activities/
```

### 出典

```text
src/content/sources/
```

### 固定ページ

```text
src/content/pages/
```

ただし、内容によってはAIに確認を依頼してください。

# 3. 🔴 原則として自分で直接変更しない場所

次のファイル・フォルダは、日常的な文章更新のために直接変更しません。

```text
src/content.config.ts
src/pages/
src/components/
src/layouts/
src/styles/global.css
src/lib/
astro.config.mjs
package.json
```

また、次のような変更も、自己判断で行わないでください。

* schemaを変更する
* 新しいfieldを作る
* policyやactivityのIDを変更する
* ファイル名を変更する
* URL構造を変更する
* 共通CSSを変更する
* 政党情報を各ページへ個別に書き換える
* パーソナルカラーを各ページへ直接書き込む
* GitHub Pagesの設定を変更する
* APIキーやパスワードをコードへ書き込む

これらは**AIに依頼してください。**

`src/content.config.ts` はContent Collectionsの実装上のschemaの正本です。政策では `relatedActivities` と `references` がCollectionのreferenceで管理され、存在しないIDを指定するとエラーになる構造です。

```text
    ↓
```

# 6. 政策を新しく作る

新しい政策ページは、次の順番で作成します。

```text
① 政策のテーマを決める
↓
② 既存政策に同じテーマがないか確認
↓
③ 必要な根拠・資料を集める
↓
④ 出典を確認
↓
⑤ 政策Markdownを作成
↓
⑥ 政策本文を書く
↓
⑦ referencesを設定
↓
⑧ 必要なら関連活動を設定
↓
⑨ 必要ならYouTubeを設定
↓
⑩ draftを確認
↓
⑪ build
↓
⑫ ブラウザで確認
```

最初に、

```text

```

似た政策がすでに存在する場合は、同じ情報を新しいページへコピーしないでください。

既存政策を更新する方が適切な場合があります。

# 7. 政策ページの基本構造

政策ページは、原則として、

```text
問題
↓
評価
↓
課題
↓
政策提案
↓
制約・限界
↓
参考資料
```

という意味構造で作成します。

サイト全体の政策構造では、

**problem → evaluation → issues → proposals → limitations**

を基本としています。

政策の提案部分は、

* `まず取り組むこと`
* `高槻市で取り組むこと`
* `大阪府・国へ要望すること`

という現在の構成を基本とします。

# 8. 政策Markdownの基本テンプレート

以下は、新しい政策を作るときの基本形です。

**注意：これは雛形です。実際に使用できる項目・形式は `src/content.config.ts` が正本です。**

```md
---
title: "政策名"
description: "政策ページの重要な概要"
heroTitle: "政策名"
heroDescription: "政策の目的と手段を簡潔に説明"
updated: "YYYY-MM-DD"
category: "カテゴリー"
tags: ["タグ1", "タグ2"]
draft: true
relatedActivities: []
references: []

problem:
  paragraphs:
    - "問題の説明"

evaluation:
  subjective:
    heading: "現場から見えること"
    paragraphs:
      - "現場経験や本人の評価"

  objective:
    heading: "公的資料から分かること"
    paragraphs:
      - "公的資料・統計等に基づく説明"

issues:
  - title: "課題1"
    description: "課題の説明"

proposals:
  - heading: "まず取り組むこと"
    items:
      - "具体的な提案"

  - heading: "高槻市で取り組むこと"
    items:
      - "具体的な提案"

  - heading: "大阪府・国へ要望すること"
    items:
      - "具体的な提案"

limitations:
  paragraphs:
    - "制約や限界"
---
```

`youtube`を追加する場合は、現在のschemaでは次の形式です。

```md
youtube:
  title: "動画タイトル"
  url: "https://www.youtube.com/..."
```

`youtube`は必須ではありません。

# 9. 政策の各項目をどう書くか

## title

政策ページの正式なタイトルです。

ページの内容を正確に表してください。

---

## description

政策ページ全体の重要な概要です。

検索結果等でも意味が伝わるように、

* 何が問題なのか
* 何を目指すのか

を簡潔に説明します。

---

## heroTitle

ページ上部に表示する政策タイトルです。

原則として政策の正式名称と一致させます。

---

## heroDescription

政策の、

* 目的
* 手段
* 目指す状態

を簡潔に説明します。

---

## updated

政策を実質的に更新した場合に更新します。

形式は、

```text
YYYY-MM-DD
```

です。

例：

```text
updated: "2026-09-18"
```

---

## category

現在登録されている政策カテゴリーを使用します。

新しいカテゴリーを勝手に作らないでください。

カテゴリーを追加・変更したい場合はAIに依頼してください。

---

## tags

政策の検索・分類に使用します。

既存タグを優先します。

タグを増やすこと自体を目的にしません。

# 10. `draft`について

政策には、

```md
draft: true
```

または、

```md
draft: false
```

を使用できます。

基本的な考え方は、

```text
true
↓
下書き

false
↓
公開対象
```

です。

新しい政策を作成した直後は、原則として、

```md
draft: true
```

にしておきます。

内容を確認して公開するときに、

```md
draft: false
```

へ変更します。

公開・非公開の実際の挙動は現在の実装に従います。

---

# 11. `references`を変更するとき

政策から出典を参照する場合は、

```md
references:
  - source-id
```

のように、既存の出典IDを指定します。

**存在しないIDを推測して書かないでください。**

Content Collectionのreferenceとして管理されているため、存在しない出典IDはschema上のエラーになります。

---

# 12. 出典を新しく追加する場合

新しい資料を使う場合、

```text
① 元資料を確認
↓
② src/content/sources/ に出典を作成
↓
③ 出典のIDを確認
↓
④ 政策のreferencesへ追加
↓
⑤ build
```

という順番にします。

出典の基本構造は、

```md
---
title: "資料タイトル"
publisher: "発行元"
year: "2026"
url: "https://..."
draft: false
---
```

です。

現在のschemaでは、

* `title`
* `publisher`
* `year`
* `url`
* `draft`

が使用されます。`url`はURL形式である必要があります。

---

# 13. 出典の選び方

政策に使用する資料は、可能な限り一次情報を優先します。

基本的な優先順位は、

1. 法律
2. 条例
3. 公的資料
4. 公的統計
5. 学術論文
6. 国際機関資料
7. 信頼できる二次資料
8. その他

とします。

特に、

* 法律
* 制度
* 統計
* 行政の対応
* 現在の料金
* 現在の制度

については、AIの記憶だけで判断しません。

# 14. 「情報源」を確認するとき

このサイトでは、情報源を明確にすることを重視します。

政策を書くときは、

```text
主張
↓
何を根拠にしているか
↓
出典
↓
元資料URL
```

という関係を追跡できる状態にしてください。

資料のタイトルだけをAIに作らせて終わりにしないでください。

元資料を確認してください。

# 15. 政策の評価を書くとき

評価には、

### 主観的評価

現場経験や本人の経験・評価。

### 客観的評価

公的資料、統計、制度等から確認できる内容。

を区別します。

現在のschemaでも、

```text
evaluation
├── subjective
└── objective
```

という構造になっています。

# 16. 政策の強い表現に注意

次のような表現は、根拠が必要です。

* 必ず
* 絶対に
* 多数
* 大幅に
* 不足している
* 全国で最も
* 全国で唯一
* 効果がある
* 効果がない

数字や比較を伴う場合は、特に出典を確認してください。

# 19. 活動の `draft`

活動を本番公開するか下書きにするかを指定します。

```yaml
draft: false
```

または `draft` 自体を省略すると、本番環境で公開されます。

まだ下書き段階で公開したくない場合は、

```yaml
draft: true
```

を設定します。本番ビルド時には除外されます。

**存在しないIDを推測しない**

# 21. 活動とSNS・YouTube

活動ページでは、現在、

```text
xUrl
instagramUrl
youtubeUrl
```

を使用できます。

SNSやYouTubeは、活動記録を補足するものです。

原則として、

```text
サイト
＝正式な活動記録

SNS・YouTube
＝入口・補助資料
```

と考えてください。

SNS投稿が削除されても、サイト側の活動記録が残る状態を優先します。

# 23. サイト全体のSNSリンクを変更する場合

サイト全体のSNSリンクは、個々のページではなく、

```text
src/data/socials.ts
```

で管理されています。

現在の共通SNS表示では、

* YouTube
* X
* Instagram
* note

が中央設定から読み込まれています。

そのため、

> 「XのURLが変わったので、Header、Footer、各ページを全部探して書き換える」

ということはしません。

**中央設定を変更する方法を優先します。**

不安な場合はAIに依頼してください。

---

# 24. 政党情報を変更する場合

政党名、政党ロゴ、公式URL等は、各ページを直接変更しないでください。

現在は、

```text
src/data/politicalAffiliation.ts
```

で中央管理する構造になっています。

Header等もこの設定を参照しています。

したがって、

```text
政党情報を変更したい
↓
個別ページを変更しない
↓
中央設定を確認
↓
AIに変更を依頼
↓
全ページへの反映を確認
```

としてください。

# 25. パーソナルカラーを変更する場合

パーソナルカラーはサイト全体で使用する個人ブランドカラーです。

現在の値は、

```text
#DC143C
```

ですが、これは将来変更する可能性があります。

正式な参照元は、

```text
src/styles/global.css
```

の、

```css
--color-personal-brand
```

です。

個別ページへ、

```css
color: #DC143C;
```

のように直接書かないでください。

変更が必要になった場合は、

```text
本人が色を決定
↓
global.cssの中央設定を変更
↓
サイト全体を確認
```

とします。

パーソナルカラーそのものをAIが独断で変更してはいけません。

```text
src/content/pages/
```

にあります。

* プライバシーポリシー

```text
title
```

# 27. 写真を変更する場合

写真を変更するときは、単純に画像だけを置き換えないでください。

確認するもの：

```text
① 画像ファイルが存在するか
② Markdownから正しく参照しているか
③ 公開後に表示されるか
④ スマートフォンでも問題ないか
⑤ 必要な代替テキストがあるか
```

画像の保存場所や参照方法が現在の実装と異なる場合は、AIに確認してください。

# 28. ファイル名とIDについて

ファイル名やIDは、単なる表示文字ではありません。

政策・活動・出典のreference関係で使用される場合があります。

そのため、

**「名前を少し分かりやすくしたい」という理由だけで変更しないでください。**

変更が必要な場合は、

```text
変更対象
↓
参照元
↓
参照先
↓
URL
↓
内部リンク
↓
build
```

まで確認する必要があります。

# 29. Markdownを編集するときの注意

Markdownファイルは基本的に、

```text
---
フロントマター
---

本文
```

という構造です。

`---` を削除したり、インデントを大きく変更したりすると、schemaエラーになることがあります。

特に、

* `:`
* `-`
* `[ ]`
* `{ }`
* `"`
* インデント
* 改行

には注意してください。

---

# 30. Markdownを直接書くのが不安な場合

無理に自分で書かなくて構いません。

AIに、

> 「この政策ページに○○を追加したい。現在のschemaを確認して、必要なファイルだけ変更してください。」

のように依頼してください。

さらに安全にするなら、

> 「変更前に変更対象ファイルを提示し、関係するファイルへの影響を確認してから変更してください。」

と依頼してください。

---

# 31. AIに依頼するときの基本形

次のように伝えると安全です。

```text
やりたいこと：
○○を変更したい。

対象：
○○ページ

条件：
・既存構造を維持
・関係ないファイルは変更しない
・現在のschemaを確認
・必要な出典を確認
・変更後にnpm run buildを実行
・変更したファイルと確認結果を報告
```

---

# 32. AIに「全部きれいにして」と頼まない

次のような依頼は避けてください。

```text
この辺を全部きれいにして
```

```text
ついでに全部改善して
```

```text
最新の方法に全部変更して
```

これらは変更範囲が広がりやすくなります。

代わりに、

```text
○○だけ変更してください。
関係ない部分は変更しないでください。
```

とします。

# 34. `npm run build`について

プロジェクトでは、


成功すれば、少なくともschemaやビルド上の重大な問題がないかを確認できます。

ただし、

ではありません。

そのため、


を行います。

# 42. 情報を複数箇所にコピーしない

# 43. 「新しいファイルを作る前」に考えること

1. 既存ページで対応できないか

3. 既存の活動ページに追加できないか
4. 既存の出典を利用できないか

を確認してください。

# 45. 「デザインを少し変えたい」とき

政党ロゴを個別ページへ貼り直さないでください。

とします。

# 54. AIに変更を依頼するときのおすすめ手順

特に大きな変更では、次の順番で依頼します。

### ① 調査

> 現在の実装を確認してください。まだ変更しないでください。

### ② 影響範囲

> 変更するとしたら、どのファイルに影響しますか？

### ③ 方針

> 既存構造を維持して、最小限の変更で実現してください。

### ④ 実装

> その方針で変更してください。

### ⑤ 検証

> npm run buildを実行して、変更箇所を確認してください。

### ⑥ 報告

> 変更したファイル、削除したファイル、build結果、未確認事項を報告してください。

# 57. AIに「buildまで」と伝える

と伝えてください。
