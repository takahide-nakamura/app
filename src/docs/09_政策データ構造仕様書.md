# 政策データ構造仕様書

## 1. 文書の目的

本書は、本Webサイトに掲載する「政策データ」の構造・意味・記述ルールを定義する正式な仕様書である。

本Webサイトでは、政策情報をAstroのContent Collectionsで管理し、政策の内容をMarkdownファイルとして保存する。

政策データは、単なるWebページの文章ではなく、

* Webページの表示
* 政策情報の整理
* 参考資料との関連付け
* 活動との関連付け
* 将来の検索機能
* 将来のSNS・動画連携
* AI（LLM）による政策データの作成・更新
* 長期的な保守・再利用

に利用される基礎データである。

したがって、本仕様書では「現在Webページに表示できればよい」という基準ではなく、**長期間にわたって人間とAIの双方が安全に扱えるデータ構造**を定義する。

---

# 2. 基本方針

政策データは、以下の原則に従って管理する。

## 2-1. データと表示を分離する

政策の内容は、原則として

`src/content/policies/`

以下のMarkdownファイルに記録する。

Astroコンポーネント側には、個別政策の文章を直接記述しない。

基本的な役割分担は以下のとおりとする。

```text
政策Markdown
    ↓
政策データ
    ↓
Content Collections
    ↓
Astroコンポーネント
    ↓
Webページ
```

政策の文章を変更する場合は、原則として政策Markdownを変更する。

表示デザインを変更する場合は、原則としてAstroコンポーネントを変更する。

---

## 2-2. データ構造を勝手に変更しない

政策Markdownに新しい項目を追加したり、既存項目の構造を変更したりする場合は、先に本仕様書を確認する。

本仕様書に定義されていない構造を、個別の政策ファイルだけに独自実装してはならない。

新しい構造が必要になった場合は、

1. 必要性を確認する
2. 既存政策への影響を確認する
3. データ構造を決定する
4. 本仕様書を更新する
5. `content.config.ts` のSchemaを更新する
6. 必要な表示側を更新する
7. `npm run build`で確認する

という順序で変更する。

---

## 2-3. AIによる編集でも本仕様を優先する

Cline、Gemini、ChatGPT、その他のAIを使用して政策データを作成・変更する場合も、本仕様書を正式なルールとして扱う。

AIの一般的な知識や提案よりも、本サイト固有の仕様を優先する。

AIが本仕様書と現在のコードの矛盾を発見した場合、独断で片方を変更せず、矛盾を報告する。

---

# 3. 政策データの保存場所

政策データは原則として以下に保存する。

```text
src/
└── content/
    └── policies/
        ├── care-certification.md
        ├── dementia-support.md
        ├── national-health-insurance.md
        ├── noise.md
        ├── garbage.md
        └── ...
```

1つのMarkdownファイルを、原則として1つの政策として扱う。

---

# 4. ファイル名のルール

政策ファイル名は、政策を識別する一意なIDとして利用される。

例：

```text
care-certification.md
dementia-support.md
national-health-insurance.md
noise.md
garbage.md
```

基本的に、

```text
小文字英数字
+
ハイフン
```

による英語のslug形式を使用する。

例：

```text
care-certification.md
```

は、

```text
care-certification
```

というIDで扱われる。

---

## 4-1. ファイル名を変更する場合

政策ファイル名の変更は、単なるファイル名変更ではない。

ファイル名は政策IDとして参照される可能性があるため、

* `relatedActivities`
* `references`
* ページURL
* `getPolicy.ts`
* その他のコード

への影響を確認する。

そのため、政策ファイル名を変更する場合は、必ずプロジェクト全体を検索して旧IDの使用箇所を確認する。

---

# 5. 政策データの全体構造

政策データは、原則として以下の構造を持つ。

```text
Policy
├── 基本情報
│   ├── title
│   ├── description
│   ├── heroTitle
│   ├── heroDescription
│   ├── updated
│   ├── category
│   └── tags
│
├── 関連情報
│   ├── relatedActivities
│   ├── references
│   └── youtube
│
├── 問題提起
│   └── problem
│       └── paragraphs[]
│
├── 評価
│   └── evaluation
│       ├── subjective
│       │   ├── heading
│       │   └── paragraphs[]
│       └── objective
│           ├── heading
│           └── paragraphs[]
│
├── 課題
│   └── issues[]
│       ├── title
│       └── description
│
├── 政策提案
│   └── proposals[]
│       ├── heading
│       └── items[]
│
└── 限界・制約
    └── limitations
        └── paragraphs[]
```

---

# 6. 基本情報

## 6-1. `title`

### 型

```text
string
```

### 必須

必須。

### 役割

政策の正式な表示名称。

### 例

```yaml
title: "要介護認定"
```

### ルール

* 政策内容を端的に表す名称とする。
* 原則として短くする。
* 政策の説明文を`title`に入れない。
* 同一Collection内で同じ政策名を乱立させない。

---

# 6-2. `description`

### 型

```text
string
```

### 必須

必須。

### 役割

政策の概要を短く説明する。

政策一覧、概要表示、SEO等で利用することを想定する。

### 例

```yaml
description: "必要な人が必要な介護サービスを適切な時期に利用できるよう、要介護認定制度の改善を提案します。"
```

### `heroDescription`との違い

`description`は、

> この政策は何についての政策なのか

を短く説明する。

`heroDescription`は、

> この政策によって何を目指すのか

を説明する。

両者を同じ文章にする必要はない。

---

# 6-3. `heroTitle`

### 型

```text
string
```

### 必須

必須。

### 役割

政策ページのHero部分に表示するタイトル。

### 例

```yaml
heroTitle: "要介護認定"
```

通常は`title`と同じでよい。

ただし、将来的に表示上のタイトルとデータ上の正式名称を分ける必要が生じる可能性があるため、独立した項目として保持する。

---

# 6-4. `heroDescription`

### 型

```text
string
```

### 必須

任意。

### 役割

政策ページのHero部分で、政策の方向性や目標を簡潔に伝える。

### 例

```yaml
heroDescription: "必要な人が、必要な介護サービスを適切な時期に受けられる仕組みを目指します。"
```

---

# 6-5. `updated`

### 型

```text
YYYY-MM-DD形式の文字列
```

### 必須

任意。

### 正式な記述形式

```yaml
updated: "2026-08-01"
```

### 許可しない形式

```text
2026/08/01
2026年8月1日
2026-8-1
2026.08.01
```

### 理由

日付形式を統一することで、

* ソート
* 比較
* 自動表示
* AIによる処理
* 将来のデータ変換

を容易にする。

将来的にはSchemaで形式を自動検証する。

---

# 6-6. `category`

### 型

```text
PolicyCategory
```

### 役割

政策の大分類。

現在の正式なカテゴリーは以下とする。

```text
🏥 医療・介護
👨‍👩‍👧 子育て
🛡️ 防災
🏙️ 暮らし
```

カテゴリーは自由入力ではない。

例えば、

```yaml
category: "医療"
```

や、

```yaml
category: "🏥 医療"
```

のような独自表記を新たに作ってはならない。

カテゴリーを追加・変更する場合は、`src/data/policyCategories.ts`と本仕様書を同時に更新する。

---

# 6-7. `tags`

### 型

```text
string[]
```

### 必須

任意。ただし現在のSchemaでは空配列をデフォルト値として扱う。

### 役割

政策を検索・分類するためのキーワード。

### 例

```yaml
tags:
  - "要介護認定"
  - "介護保険"
  - "介護"
  - "高齢者"
  - "老後"
```

### `category`との違い

`category`は大分類。

`tags`は検索・関連付けのための細かなキーワード。

したがって、カテゴリーをタグの代わりに使用したり、タグをカテゴリーの代わりに使用したりしない。

---

# 7. 関連情報

## 7-1. `relatedActivities`

### 型

```text
Activity ID[]
```

### 役割

政策に関連する活動データを参照する。

### 例

```yaml
relatedActivities:
  - nursing-care-visit
```

これは活動名を直接記述するものではない。

```text
nursing-care-visit
```

というIDを指定して、Activities Collectionのデータを参照する。

### 禁止例

```yaml
relatedActivities:
  - "訪問リハビリテーション"
```

活動名そのものを記述してはならない。

### 重要

現在のコードでは、関連IDが存在しない場合に単純に表示されない可能性がある。

将来的なSchema強化では、存在しないActivity IDを指定した場合にビルド時に検出できる構造へ移行する。

---

# 7-2. `references`

### 型

```text
Source ID[]
```

### 役割

政策の根拠・参考資料をSources Collectionから参照する。

### 例

```yaml
references:
  - takatsuki-audit-2025
```

これは資料名やURLを直接書くものではない。

Sources Collectionに存在するIDを指定する。

### 禁止例

```yaml
references:
  - "高槻市監査委員報告書"
```

```yaml
references:
  - "https://example.com/..."
```

政策Markdown内に直接URLを書いて参考資料として管理する方式は原則として採用しない。

---

# 8. `youtube`

### 型

```text
YouTube
├── title: string
└── url: URL
```

### 必須

任意。

### 例

```yaml
youtube:
  title: "要介護認定について解説"
  url: "https://www.youtube.com/..."
```

### ルール

YouTube動画が存在しない場合は、`youtube`そのものを省略する。

動画がない状態で無意味な空オブジェクトを作らない。

---

# 9. 問題提起 `problem`

## 構造

```yaml
problem:
  paragraphs:
    - "文章1"
    - "文章2"
    - "文章3"
```

### 型

```text
Problem
└── paragraphs: string[]
```

### 役割

政策が扱う問題・背景を説明する。

### 答える質問

```text
「なぜ、この政策を考える必要があるのか？」
```

に答える部分。

### 内容

* 市民が直面している問題
* 制度上の問題
* 地域社会の問題
* 将来的な問題
* 政策として取り組む必要性

などを記載する。

### `issues`との違い

`problem`は問題の背景・全体像。

`issues`は、その問題を具体的な政策課題へ分解したもの。

---

# 10. `problem.paragraphs`

### 型

```text
string[]
```

### ルール

配列の1要素を原則として1段落とする。

例：

```yaml
problem:
  paragraphs:
    - "第1段落。"
    - "第2段落。"
    - "第3段落。"
```

文章を1つの巨大な文字列にまとめない。

---

# 11. `evaluation`

`evaluation`は、政策について「どのように評価できるか」を整理する。

正式な構造は以下。

```text
evaluation
├── subjective
│   ├── heading
│   └── paragraphs[]
│
└── objective
    ├── heading
    └── paragraphs[]
```

---

# 12. `evaluation.subjective`

### 役割

現場経験・職務経験等から得られた認識を記載する。

本サイトでは、理学療法士としての現場経験などを記載する場所として利用する。

### 構造

```yaml
subjective:
  heading: "現場で感じること"
  paragraphs:
    - "..."
    - "..."
```

### 注意

「subjective」は「根拠のない意見」という意味ではない。

実際の現場経験に基づく認識・経験知を整理するための領域である。

ただし、統計・制度・法令等の客観的事実を主観セクションだけで説明することは避ける。

---

# 13. `evaluation.objective`

### 役割

公的資料、統計、制度資料、調査等から確認できる情報を記載する。

### 構造

```yaml
objective:
  heading: "公的資料から分かること"
  paragraphs:
    - "..."
    - "..."
```

### 重要ルール

客観的な事実、数値、制度、法律、行政の取組等を記載する場合は、可能な限り`references`によって根拠を追跡できる状態にする。

特に、

* 数値
* 制度内容
* 法律
* 行政計画
* 公的機関の見解
* 統計
* 効果・リスクに関する主張

については、根拠を確認する。

---

# 14. `issues`

### 型

```text
Issue[]
```

### 構造

```yaml
issues:
  - title: "課題タイトル"
    description: "課題の説明"
```

### 各要素

```text
Issue
├── title: string
└── description: string
```

### 役割

`problem`で提示した問題を、具体的な政策課題に分解する。

基本的な関係は、

```text
problem
↓
問題・背景
↓
issues
↓
具体的な課題
↓
proposals
↓
具体的な政策
```

とする。

---

# 15. `proposals`

### 型

```text
Proposal[]
```

### 構造

```yaml
proposals:
  - heading: "今すぐ取り組めること"
    items:
      - "..."
      - "..."
```

### 各要素

```text
Proposal
├── heading: string
└── items: string[]
```

---

# 16. `proposals`の基本分類

現在の標準構成は以下。

```text
1. 今すぐ取り組めること
2. 高槻市として取り組むこと
3. 大阪府・国へ要望すること
```

### 1. 今すぐ取り組めること

行政や議会活動等を通じて、比較的短期に取り組める事項。

### 2. 高槻市として取り組むこと

高槻市の権限・予算・事業・行政運営等によって取り組む事項。

### 3. 大阪府・国へ要望すること

高槻市単独では決定できない制度・法律・財源等について、大阪府や国へ要望する事項。

---

# 17. `proposals.heading`は固定値ではない

現在は3分類を標準として使用するが、Schema上で必ずこの3つだけを許可する仕様にはしない。

理由は、将来政策によって適切な分類が変わる可能性があるため。

ただし、独自のheadingを使用する場合は、

> なぜ既存の3分類では整理できないのか

を確認する。

同じ意味の分類を別表現で乱立させない。

例えば、

```text
高槻市でやること
高槻市が取り組むこと
高槻市として実施すること
```

を政策ごとに自由に使い分けることは避ける。

---

# 18. `limitations`

### 型

```text
Limitations
└── paragraphs: string[]
```

### 構造

```yaml
limitations:
  paragraphs:
    - "..."
    - "..."
```

### 役割

政策について、

* 高槻市だけでは変更できない制度
* 国の法律による制約
* 大阪府の権限に関係する事項
* 現時点で実現が難しい事項
* 政策によって解決できない範囲
* 実施時に考慮すべき制約

などを明示する。

### 特に重要な考え方

`limitations`は「政策の弱点を書く場所」ではない。

**政策を実現できる範囲を正確に示すための項目**である。

例えば、

```text
全国共通の法律に基づく制度なので、
高槻市だけでは制度そのものを変更できない。
```

という情報は、政策の信頼性を高めるために重要である。

---

# 19. 政策データの論理構造

政策データ全体は、以下の順番で理解する。

```text
① problem
「何が問題なのか」

        ↓

② evaluation
「現場から見るとどうなのか」
「公的資料から見るとどうなのか」

        ↓

③ issues
「具体的に何が課題なのか」

        ↓

④ proposals
「具体的に何をするのか」

        ↓

⑤ limitations
「何ができて、何ができないのか」
```

この順番は政策ページの単なる表示順ではなく、**政策を構造化する基本的な論理関係**として扱う。

# 21. 空データの扱い

現在の設計では、以下の項目は空配列を許容する。

```yaml
tags: []
relatedActivities: []
references: []
```

例えば、

```yaml
relatedActivities: []
```

は正常なデータである。

「関連活動が存在しない」という意味で使用する。

一方、

```yaml
relatedActivities:
```

のような値がない状態を意図的に作らない。

---

# 22. 任意項目の扱い

以下は任意項目として扱う。

```text
heroDescription
updated
category
youtube
problem
evaluation
issues
proposals
limitations
```

ただし、「任意だから何でもよい」という意味ではない。

政策の内容に応じて必要な項目を適切に記載する。

# 23. AIが政策を新規作成するときのルール

AIに新しい政策ページを作成させる場合、以下の順序で作業する。

### Step 1

既存の政策Markdownを確認する。

### Step 2

本仕様書を確認する。

### Step 3

政策IDを決定する。

### Step 4

基本情報を作成する。

### Step 5

問題を`problem`に整理する。

### Step 6

現場経験と公的資料を`evaluation`に分ける。

### Step 7

具体的な課題を`issues`に整理する。

### Step 8

政策提案を`proposals`に整理する。

### Step 9

高槻市だけでは解決できない事項を`limitations`に整理する。

### Step 10

関連活動・参考資料が存在する場合はIDで参照する。

### Step 11

既存のSchemaと矛盾しないことを確認する。

### Step 12

`npm run build`を実行して確認する。

---

# 24. AIが絶対に勝手に行ってはいけない変更

AIは、政策追加・修正時に以下を独断で行ってはならない。

### 24-1. フィールド名を変更する

例えば、

```yaml
problem:
```

を

```yaml
background:
```

に変更してはならない。

---

### 24-2. 同じ意味の新しいフィールドを作る

例えば、

```yaml
problem:
```

が存在するのに、

```yaml
background:
```

を新設してはならない。

---

### 24-3. 配列構造を勝手に変更する

例えば、

```yaml
problem:
  paragraphs:
    - "..."
```

を、

```yaml
problem: "..."
```

に変更してはならない。

---

### 24-4. ID参照を名称参照に変更する

```yaml
relatedActivities:
  - nursing-care-visit
```

を、

```yaml
relatedActivities:
  - "訪問リハビリテーション"
```

に変更してはならない。

---

### 24-5. URLを直接埋め込む

`references`には原則としてURLを直接記述しない。

Sources CollectionのIDを参照する。

---

### 24-6. 既存政策だけ独自構造にする

新しい構造が必要なら、個別政策だけに追加するのではなく、正式仕様を見直す。

---

# 25. 既存政策を編集するときのルール

文章を修正する場合でも、まず構造を維持できるか確認する。

例えば、

```yaml
problem:
  paragraphs:
```

という構造自体を変更せず、

```yaml
problem:
  paragraphs:
    - "修正した文章"
```

のように内容だけ変更する。

構造変更が必要な場合は、本仕様書・Schema・表示側への影響を確認する。

---

# 26. 政策データと事実確認のルール

政策データは政治的主張を含むため、特に客観情報については注意する。

以下のような情報をAIが生成する場合、事実確認なしに断定的に記載しない。

* 統計値
* 制度の内容
* 法律の内容
* 高槻市の現行制度
* 大阪府の制度
* 国の制度
* 予算
* 金額
* 件数
* 効果
* 医学・健康に関する事実
* 「全国初」「全国最大」等の比較表現

確認できない情報は、推測で補完しない。

---

# 27. `references`と`objective`の関係

`objective`に客観的事実を記載する場合、その根拠を可能な限り`references`に登録する。

基本的な関係は、

```text
objective
    ↓
客観的情報
    ↓
references
    ↓
sources
    ↓
具体的な公的資料・情報源
```

とする。

これによって、将来、

> 「この政策のこの記述は何を根拠にしているのか？」

を追跡できる。

---

# 28. `references`と`problem`・`proposals`の関係

すべての文章が必ず参考資料を必要とするわけではない。

例えば、

> 「私は理学療法士としてこう感じている」

という経験談は、必ずしも公的資料の引用を必要としない。

一方、

> 「高槻市では○○％である」

という数値には根拠が必要である。

したがって、

```text
subjective
↓
本人の経験・認識

objective
↓
公的・客観的情報
↓
referencesで根拠を確認
```

という使い分けを基本とする。

---

# 29. Schemaとの関係

本仕様書は「人間とAI向けの設計仕様」であり、実際のプログラムによる入力チェックは`src/content.config.ts`が担当する。

役割分担は以下。

```text
政策データ構造仕様書
↓
人間・AIが理解する正式仕様

content.config.ts
↓
プログラムによる形式チェック

政策Markdown
↓
実際のデータ

Astro
↓
Web表示
```

本仕様書とSchemaは同じルールを共有する。

将来的に両者が矛盾した場合は、矛盾を放置せず、どちらを正式仕様とするか確認して修正する。

---

# 30. Schema変更時の原則

今後、`content.config.ts`を変更する場合は、以下の順序を基本とする。

```text
① 変更理由を明確化
↓
② 本仕様書への影響確認
↓
③ データ構造を決定
↓
④ 本仕様書を更新
↓
⑤ content.config.tsを更新
↓
⑥ 既存Markdownを確認
↓
⑦ 必要なコードを更新
↓
⑧ npm run build
↓
⑨ Web表示確認
```

Schemaだけ変更して終わりにしない。

# 32. 後方互換性を重視する

長期運用では、「新しい設計がきれいだから」という理由だけで既存データを全面的に変更しない。

特に、

* フィールド名
* ID
* ファイル名
* URL
* データ構造

は変更による影響が大きい。

変更する場合は、

```text

↓
新データ
```

を明確にする。

# 33. 20年運用における重要原則

本サイトでは、短期的な開発効率よりも、長期的な理解可能性・修正可能性を重視する。

特に重要なのは以下。

### 原則1

**分からない構造を作らない。**

### 原則2

**同じ意味のデータを複数の場所に重複して持たない。**

### 原則3

**文字列で済ませられるものを過度に複雑な構造にしない。**

### 原則4

**一方で、将来重要になる参照関係はIDとして明確にする。**

### 原則5

**AIが推測しなくても理解できる構造にする。**

### 原則6

**人間がコードを読めなくても、仕様書を読めばデータ構造を理解できるようにする。**

### 原則7

**変更する場合は、既存データへの影響を確認してから変更する。**

# 34. 政策データの最終的な考え方

本サイトにおける政策データは、

```text
単なるWebページの文章
```

ではない。

以下を兼ね備えた「構造化された政策情報」として扱う。

```text
政策情報
+
現場経験
+
客観的根拠
+
課題
+
政策提案
+
実現可能範囲
+
関連活動
+
参考資料
```

この構造を維持することで、将来的にWebサイトの表示方法が変わっても、政策データそのものを再利用できるようにする。

# 38. 仕様書を変更する場合

本仕様書は完成後も永久に変更禁止とするものではない。

ただし、変更する場合は、

1. なぜ変更するのか
2. 現在のデータにどのような影響があるか
3. コードにどのような影響があるか
4. AIによる生成ルールにどのような影響があるか
5. 既存政策を移行する必要があるか

を確認する。

特に20年運用を想定するため、**「今のコードをきれいにする」ことより「将来の変更による破壊を最小化する」ことを優先する。**

# 39. 最終原則

このプロジェクトでは、

> **政策データの構造を先に決め、その構造にコードを合わせる。**

という考え方を基本とする。

AIにコードを書かせる場合も、

> 「AIがうまく判断してくれること」

を期待するのではなく、

> **「AIが判断しなくても正しく作れる仕様にしておくこと」**

を目指す。

これを本サイトの長期運用における基本原則とする。
