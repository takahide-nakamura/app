# 設計原則

この文書は、このサイトの「変わらない原則」を定義する。ここに書く内容は、長期運用を前提にした基本方針であり、実装の詳細や日々の編集手順は別の文書に分ける。

---

## 1. サイトの目的

このサイトは、政策・活動・出典を整理して市民に伝えるための情報基盤である。

- 政策の背景と課題をわかりやすく伝える
- 根拠となる資料を明示する
- 市民生活に関する活動を見つけやすくする
- 長期的に更新しやすい構造を維持する

## 2. 実施上の必須原則

次の原則は、すべての編集・AI実装・保守作業に適用する。

### 2-1. 事実と意見を分ける

- 事実は公的資料や統計などの根拠に基づく
- 評価はその事実から導かれる判断として明示する
- 提案は改善方向として別に書く
- 「感想」や「推測」を事実として扱わない

### 2-2. 参考資料を必ず残す

- すべての政策は出典や参考資料を持つことを原則とする
- 出典は sources コレクションで管理する
- 出典がない主張は、根拠不明として扱う

### 2-3. フィールド名と構造を固定する

- 新しいフィールド名を勝手に増やさない
- 既存の構造を変えない
- 実装と文書の整合を確認してから変更する

### 2-4. Markdown を中心に更新する

- 一般編集者は src/content 配下の Markdown を直接編集する
- エンジニアでない人が直接コーディングしなくてよい前提で設計する
- UIやコード変更は、必要時のみ行う

### 2-5. 変更は小さく行う

- 一度に大きく構造を変えない
- 影響範囲を確認してから修正する
- 対象ファイルと関連ファイルをセットで確認する

## 3. 現行実装との整合

このプロジェクトは、Astro + TypeScript + Content Collections を使っている。

- 政策・活動・出典はそれぞれ独立した Collection を扱う
- 政策は relatedActivities と references で関連付ける
- 実装上の厳密な型は src/content.config.ts を正とする
- 仕様書と実装に差異があれば、実装側を優先して確認する

## 4. 禁止事項

以下は原則として禁止する。

- 新しいデータフィールドを勝手に作る
- 仕様書を見ずに独自の構造を追加する
- AI が根拠のない事実を補う
- 実在しない activities / sources ID を関連付ける
- 「とりあえずいい感じ」で文章を増やす

## 5. 文書の責務分担

- 01 設計原則: 変わらない基本方針
- 02 コンテンツ執筆ルール: 政策・活動・出典の書き方
- 03 エビデンス運用ルール: 出典・根拠・事実の扱い
- 04 UI・デザインルール: 見出しとレイアウトの基本
- 05 アクセシビリティチェック: 読みやすさと利用しやすさ
- 06 SEO・情報設計: 検索と情報整理
- 07 公開・保守手順: 更新手順と確認手順
- 08 AI運用ルール: AI の作業ルール
- 09 政策データ構造仕様書: 実際のデータ構造の定義

## 6. 変更時の判断基準

設計変更が必要になった場合は、次の順で判断する。

1. 既存の構造と実装を確認する
2. 現在のデータスキーマを確認する
3. 既存コンテンツへの影響を確認する
4. 変更後の文書と実装を整合させる
5. npm run build で確認する

この順序を守らない変更は、原則として認めない。
